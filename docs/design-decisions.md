# 两项关键设计决策

本文记录拖拽查询内核在两个问题上的取舍：**模式（schema）怎么定位**，以及
**一对多关联下怎么防止"一"侧度量被重复计数**。两项都不止一种可行做法，
这里写明最终选择、理由与代价，便于后续评审与改动。

相关代码：

- 模式定位：`app/modeling/schema.py`（`TableSpec.qname`）、
  `app/expressions/sandbox.py`（`quote_ref`）、
  `app/modeling/catalog.py`（`column_index` 回填 `schema_name`）、
  `app/sqlgen/graph.py`（`JoinEdge.on_clause`）、
  `app/sqlgen/generator.py`（所有 `FROM/JOIN` 经 `_qname` 全限定）。
- 防重复计数：`app/sqlgen/generator.py`（`_fanout_measure_tables` /
  `_render_with_dedup`）。

---

## 决策一：表归属哪个模式，以模型登记为准，语句一律写全限定名

### 问题

样例库的表都建在 `biz` 模式下，而服务账号的默认 `search_path` 是
`"$user", public`，不含 `biz`。生成的 SQL 只写裸表名（`FROM "orders"`），
Postgres 在搜索路径上找不到表，于是所有查询和筛选枚举都报
`relation "orders" does not exist`。建模页又允许从**别的模式**导入表，
因此"所有表恰好都在同一个模式里"并不是一个可以依赖的前提。

### 备选方案

1. **连接层设搜索路径**：连接建立时 `SET search_path TO biz, public`
   （或在连接串/`options` 里带 `-c search_path=...`）。
2. **语句里写全限定名**：`"schema"."table"`，模式取自模型里每张表登记的
   `schema_name`。
3. 裸表名 + 让用户/运维保证默认搜索路径。

### 选择：方案 2（全限定名）

所有物理表引用都发全限定名，模式来源是模型中的 `TableSpec.schema_name`，
而不是会话状态：

- 表达式里的物理列：`FieldRef` 新增 `schema_name`，编译时
  `"biz"."orders"."total_amount"`；
- `FROM / LEFT JOIN`：`"biz"."orders"`；
- 枚举下拉、去重派生表内层同理。

### 理由

- **模式归属是语义模型的一部分**。建模页既然能从不同模式导入表，两张同名
  表（`biz.audit_log` 与 `ext.audit_log`）就必须能被模型精确区分；搜索路径
  只能给一个全局顺序，无法表达"这张模型表来自那个模式"。
- **查询与会话解耦**。同一份模型无论被哪个账号、哪条连接、哪个默认
  search_path 执行，结果都一致；连接池新建/重连、换库迁移、用只读账号
  直连都不需要额外设置。这正是本次"分析师临时在会话里补 search_path 才好
  一半"的根治办法——不再依赖任何会话前提。
- **安全/可移植性更好**：不依赖运行时 `SET`，不被别人改过的 search_path
  影响；导出 SQL 到其他工具直接可跑。

### 代价

- 生成的 SQL 更长、更啰嗦（每个表名都带模式）；阅读时噪音略增。可接受——
  这是给机器执行、给人"预览"的文本，且已通过统一的 `_qname` / `quote_ref`
  收口。
- 标识符需要正确转义（模式名/表名中的双引号）。已集中在
  `quote_ident` 一处处理，配合建模校验器对名字的约束，属于纵深防御。
- 模型里的 `schema_name` 必须与物理库一致；表被移动到别的模式后，需要在
  建模页更新登记（本来导入表就是以模型为准，语义自洽）。

> 没有采用连接层 search_path 的根本原因：它是**全局、单模式优先**的机制，
> 表达不了"一次查询里的不同表来自不同模式"，而这是建模页明确支持的场景。
> search_path 只适合"一套库一个模式"的简单部署，作为全限定名的补充（让人
> 手工写 SQL 时方便）可以，但不能作为本工具正确性的依赖。

## 决策二：一对多下防重复计数——保留"按主键去重的派生表"

### 问题

`orders 1:N order_items`。按商品品类汇总订单总额时，
`orders.total_amount` 会随明细行被复制：

- 直接连接后求和：外设 **24513**、配件 **16989**（错误，含多品类/多明细
  订单的重复累加）；
- 正确口径（每张订单对它涉及的每个品类只计一次）：外设 **15618**、
  家具 **4123**、电脑 **19724**、配件 **12533**。

`orders 1:N payments` 同理（分期订单的金额会被多笔支付复制）。

### 备选结构

1. **按主键去重的派生表**（现有方向，本次修复后保留）：
   内层 `SELECT DISTINCT 维度, 度量表主键, 度量基列 [, 过滤标志]`，
   先消除 JOIN 复制，外层再按维度聚合。
2. **先在度量表粒度聚合再挂回维度**：度量在其所在表（按维度外键）先
   `GROUP BY` 成一张小表，再和维度表连接。
3. 相关子查询 / LATERAL：每个度量写成
   `(SELECT SUM(...) FROM ... WHERE ...)`。

### 选择：方案 1（按主键去重派生表），并修正其中的作用域与过滤缺陷

保留派生表思路，但把两处真实缺陷修掉：

- **派生表作用域**：中层查询的 `FROM` 是 `__dedup` 子查询，物理表名已离开
  作用域。原实现中层仍写 `"products"."category"`，Postgres 报
  `missing FROM-clause entry`。现在维度在内层 `DISTINCT` 时就起好输出别名
  （`... AS "dim_product_category"`），中层和回连条件一律引用该别名。
- **度量过滤**：原来度量筛选（如订单总额 > 1000）参数被绑定却没有任何
  子句引用。现在统一在"聚合完成之后"包一层，对聚合列别名做过滤
  （`WHERE "m_order_total" > $n`），扁平与去重两条路径同一套写法，参数必然
  被使用；且排序与 `LIMIT` 只放在最外层，避免"先 LIMIT 再过滤"把本该保留
  的分组提前裁掉。

### 为什么不换成方案 2（度量表粒度预聚合）

方案 2 在**维度来自度量表的多对一上游**时（品类对销量、大区对订单额）很
自然；但本工具的维度可以来自任意可达表，且一次查询常出现
**多个"多侧分支"**（明细和支付都是订单的多侧）。预聚合要为每种维度/分支
组合分别推导外键分组键，路径复杂且容易再次相乘。按主键去重的派生表有两个
关键优点：

- **与 JOIN 推导正交**：无论维度在哪张表、生成树怎么长，只要把会被复制的
  度量表识别出来（`_fanout_measure_tables` 沿生成树逐边判断基数），对该表
  做 `DISTINCT 维度, 主键, 值` 即可，逻辑统一。
- **多分支天然不相乘**：每个风险度量表各走一个派生表（`r1`/`r2`…），
  明细侧的放大与支付侧的放大互不影响。

### 代价（要让使用者知道的口径含义）

去重保证的是"**每个维度值内**，一侧度量不被复制"，它**不保证各维度值可以
相加对账**。当一张订单跨多个品类时，该订单的总额会在它涉及的**每一个**
品类下各计一次：

- 样例中品类合计 = **51998**，而全部订单总额 = **32274**
  （51998 = 32274 + 多品类订单的重复份额）。

这不是计算错误，而是"按品类归因订单金额"的**分配/归属口径**：要回答
"每个品类贡献了多少订单金额"，一张多品类订单本就应计入多个品类。但它
**不能**用来和"全公司订单总额"对账。

**界面提示（已实现）**：当查询命中一对多去重（响应里的 `fanout_tables`
非空）时，结果区上方显示一条非阻断提示，说明：一侧度量对每个维度值只计
一次、各维度值之间不可横向相加对账（并给出"一张订单含多个品类时品类合计
会大于订单总额"的例子）。我们选择**提示而非静默改写或禁止**，因为：

- 该口径在"品类贡献"类分析中是正确且常用的，禁止会损失合法分析能力；
- 静默把数字改成全局可加的分摊（如按明细金额比例拆分订单总额）会引入模型
  未声明的假设，且让总额依赖分摊规则，反而更难解释；
- 明确告知口径与不可加性，把"是否需要分摊"留给分析师/建模者决定。

若业务确实需要"可加、能对账到总额"的数字，应使用多侧原生度量（如
`销售额 = SUM(quantity * unit_price)`、`支付金额`），它们在明细表/支付表
粒度天然可加；订单总额这类"一侧表头金额"仅适合按一侧维度（如客户、订单
状态、时间）汇总，或在跨多品类时按归因口径解读。
